# 0.15.1 补充包撤销过渡修复

## 原因

Steamodded 26.829.0 对 `Game:update` 的补丁在状态 `SMODS_BOOSTER_OPENED`（999）中直接调用 `SMODS.OPENED_BOOSTER.config.center:update_pack(dt)`。

Oracle 0.15.0 在请求撤销时清空了 `SMODS.OPENED_BOOSTER`，但 `G.FUNCS.start_run` 只是排队执行旧局删除与新局加载，尚未改变当前状态。两次事件之间的一帧仍进入补充包更新，于是出现 `game.lua:2712: attempt to index field 'OPENED_BOOSTER' (a nil value)`。暂停只把 dt 置为零，不会阻止这段状态分派。

这是 Oracle 自身的状态切换缺陷，可以在已验证的 Steamodded 版本复现；不能据此归因于其他模组。

## 修复

- 撤销请求通过节点校验和保存队列提交后，在清空旧局引用前，将 `G.STATE` 置为原版 `Game:delete_run` 使用的 `-1` 过渡值。
- 仍执行原版每帧更新与加载事件，不暂停整个更新函数，不伪造补充包对象，不捕获并吞掉原版异常。
- 新局状态仅由原版加载器从目标快照建立；不让旧手牌、商店、结算或补充包处理器在清理过程中重新运行。
- 恢复期间再次按 F9 直接返回，避免重入或打开暂停面板干扰加载。
- 节点格式不变，沿用现有历史；中文简介和原有快捷预测保留。

## 验证

从本机 Lovely dump 提取实际的补充包更新分派语句，并在撤销请求、删除旧局、加载目标节点之间逐帧执行。新增回归在未修复代码上复现相同的 `OPENED_BOOSTER` 空值堆栈，修复后通过。

覆盖 SMODS 状态及五种原版补充包状态；dt 为 0、0.00421868、1、10，共 24 组状态／帧间隔组合。验证正常开包更新仍被调用，撤销过渡中不再调用旧包逻辑，恢复后商店状态、金钱、RNG 和历史栈正确。F9 测试覆盖恢复期间重复按键。

这验证了状态切换与实际原版分派代码；完整图形加载、More Speed、JokerDisplay 和 DVPreview 的组合环境仍需实机复验。未修改这些模组或放宽版本检查。
